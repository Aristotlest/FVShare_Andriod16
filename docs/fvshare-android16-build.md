# FVShare Android 16 兼容构建说明

## 1. 文档目的

当前最新产物为 `FVShare_Android16_compat7.apk`（versionCode 251）。用户已反馈小米14、小米17ultra、澎湃4.0.5.0 上扫描、连接、云台控制及拍摄均正常；发布助手未独立复测。下文保留早期构建历史，其中“待真机验证”描述的是当时状态；最新验证以仓库 README 为准。恢复到 compat7 时必须按 README 的完整补丁顺序操作。

记录已直接执行的二进制兼容改造、可恢复构建入口及验收边界。交付物是待真机验证的兼容测试版，不是完成全面依赖升级的原厂新版。

## 2. 背景与输入依据

### 2.1 用户需求摘要

为 VILTA-M 在小米 17 Ultra、Android 16、澎湃 OS 3.0.312.0 上恢复 FVShare 使用。用户明确授权直接执行，无需 DSH。

### 2.2 已参考文档

- 全局架构师及工作区规范：执行授权、保留原始文件、维护恢复记录。
- `docs/implementation-guide.md`：现有内容涉及模型配置，与本任务无关，保留。
- Pdfium 候选仓库 Java 源码、构建声明和许可证：确认 JNI 参数和库加载方式。

### 2.3 关键代码与配置位置

- `FVShare_2.4.5_APKPure.xapk`：原始输入。
- `FVShare_2.4.5_original.apk`：原始 APK。
- `prepare_compat.py`：兼容修改脚本。
- `/tmp/opencode/fvshare-decoded`：实际反编译及修改树，临时目录可能被清理。
- `/tmp/opencode/pdfium-candidate`：候选 ARM64 原生库与 Java 源码。
- `compat-build-report.json`：库哈希、来源及保留资源记录。

### 2.4 信息冲突与采用结论

没有原厂源码或 Gradle 依赖声明，不能进行常规全量依赖升级。采用局部二进制修复，保留 target SDK 28；支持 Android 16 运行不等同于以 API 36 为目标构建。

## 3. 需求分析

### 3.1 业务目标

交付可直接安装的 ARM64 测试 APK，再用真机验证启动与 VILTA-M 控制。

### 3.2 功能需求

修复 PDF 原生库的页对齐、移除文件描述符隐藏字段反射、内置 OBB 资源、请求精确位置以支持旧目标 SDK 下的 BLE 扫描。

### 3.3 非功能需求

保留原始输入，独立签名，记录候选版本来源和测试结果。

### 3.4 范围边界

仅 ARM64 手机；没有更改云台协议、服务器或云台固件逻辑。原有原生相机/视频库及 Java UI 库未整体升级。

### 3.5 验收标准

- 构建、ZIP 校验、签名和本地库依赖检查通过。
- 所有 ARM64 ELF LOAD 段满足 16 KB 对齐及地址/偏移同余。
- 音频资源不压缩，可供 `AssetManager.openFd` 读取。
- 真机可安装、冷启动、打开帮助 PDF、扫描/连接 VILTA-M、控制及拍摄；这些标准尚未验证。

### 3.6 假设与待确认项

手机实际页大小未知。签名校验、Android 16 厂商差异、旧 SDK 权限行为及联网服务仍需实际运行检查。

## 4. 当前状态与影响分析

### 4.1 当前实现行为

原版 target 28 / min 21；三个 PDF 依赖库 LOAD 对齐 4096。原版 PDF 通过隐藏字段获取 fd；启动只请求粗略位置。资源管理器优先查 APK assets，否则读取依赖 Google 下载数据库的 OBB。

### 4.2 受影响模块与文件

`PdfiumCore.smali`、`LocalResourceManager.smali`、`FVSplashActivity.smali`、`apktool.yml`、ARM64 lib 和 assets。

### 4.3 接口、数据模型和配置影响

保留原包名、版本代码 245 和原有 JNI 签名；版本名称为 `2.4.5-a16-compat1`。签名变为本地证书。

### 4.4 兼容性与回归影响

不能覆盖安装原厂签名版本。候选库 JNI 导出及 Java 参数已核对，但 PDF 实际渲染仍待真机验证。

## 5. 推荐实施策略

### 5.1 总体方案

使用 Apktool 3.0.3 解包，局部修改并打包；用 uber-apk-signer 1.3.0 对齐、签名及验证。

### 5.2 实施步骤

#### 步骤 1：分析与工具准备（已完成）

- 目标：定位兼容问题。
- 涉及文件：原始 XAPK、反编译清单、Java/Smali、ELF。
- 具体修改：下载工具及候选库至临时工作目录。
- 实现要点：候选来源固定为 `appuraja1/PdfiumAndroid-16kb` 提交 `8037a684c47fec2e62ec3e9e89e616eac0d596dd`。
- 错误处理与边界条件：网络下载失败后通过 GitHub blob API 取得文件，不关闭 TLS 验证。
- 测试要求：检查库架构、JNI、依赖与对齐。
- 完成标准：已通过。

#### 步骤 2：兼容修改（已完成）

- 目标：构建单 APK ARM64 兼容版。
- 涉及文件：`prepare_compat.py` 和反编译树。
- 具体修改：替换四个 PDF 库并添加 C++ 运行库；提供与 SONAME 匹配的别名库；使用公开 `getFd()`；合并 OBB；精确位置权限；设置版本名称。
- 实现要点：assets 优先加载路径已存在；资源到位检查改为实际检测内置 `updateinfo.json`，不无条件返回成功。
- 错误处理与边界条件：OBB 与 APK 中三个固件文件冲突时保留 APK 原版，不替换固件。构建中只保留 ARM64 库。
- 测试要求：Smali 编译、资源打包、ZIP/ELF 检查。
- 完成标准：已通过。

#### 步骤 3：构建签名（已完成）

- 目标：生成安装产物。
- 涉及文件：`FVShare_Android16_compat1.apk`。
- 具体修改：新本地证书签名。
- 实现要点：原生库压缩打包，由系统提取，不依赖 ZIP 内原生库的直接 mmap 对齐。
- 错误处理与边界条件：保留原 APK，不覆盖同名交付文件。
- 测试要求：v1/v2/v3 签名、ZIP CRC、打包依赖检查。
- 完成标准：已通过；签名工具提示一条 warning，未输出具体内容，不能宣称无警告。

#### 步骤 4：真机验收（待验证）

- 目标：确认恢复使用。
- 涉及文件：测试 APK 和启动/连接日志。
- 具体修改：根据实际失败路径决定后续修复。
- 实现要点：先安装和启动，再扫描连接，最后验证拍摄、PDF、重连。
- 错误处理与边界条件：失败时保留完整系统错误及必要日志；不推定失败原因。
- 测试要求：用户安装测试，或连接手机后准备 ADB 执行验证。
- 完成标准：上述功能真机通过，当前未达到。

### 5.3 关键技术决策

| 决策 | 采用方案 | 理由 | 替代方案及不采用原因 |
| --- | --- | --- | --- |
| 目标 SDK | 保留 28 | 避免混入存储、媒体、蓝牙等行为迁移 | 直接设 36 无法代表完成适配 |
| PDF 库 | 固定提交的 16 KB 构建 | JNI 导出及参数可核对 | 全部换最新版缺少接口与源码依据 |
| OBB | 合并 assets | 原资源加载器已有 assets 优先路径 | 单独部署增加现代 Android 文件访问步骤 |

## 6. 执行说明

### 6.1 实施前必读内容

本说明、任务进度、修改脚本及报告。

### 6.2 实施顺序

恢复构建时从原 APK 重新反编译，执行修改脚本，再构建签名；不得向已有修改树重复追加 YAML 配置。

### 6.3 实施约束

### 6.4 完成后必须汇报

## 7. 验证与测试计划

### 7.1 自动化测试

已执行构建入口：

```bash
java -jar /tmp/opencode/apktool_3.0.3.jar d FVShare_2.4.5_original.apk -o /tmp/opencode/fvshare-decoded
python3 prepare_compat.py /tmp/opencode/fvshare-decoded /tmp/opencode/pdfium-candidate
java -jar /tmp/opencode/apktool_3.0.3.jar b /tmp/opencode/fvshare-decoded -o /tmp/opencode/FVShare_Android16_unsigned.apk
java -jar /tmp/opencode/uber-apk-signer-1.3.0.jar -a /tmp/opencode/FVShare_Android16_unsigned.apk --ksDebug /tmp/opencode/fvshare-compat.keystore -o /tmp/opencode/fvshare-signed
```

路径必须仍存在；解包输出目录已经存在时，不可直接重复上述第一条。

### 7.2 手动验证

安装 APK；允许相机、麦克风和精确位置；打开蓝牙与系统定位；验证主页、VILTA-M 扫描连接、控制、拍摄、PDF、断线重连。

### 7.3 边界与失败场景

离线启动、拒绝位置后重新授权、蓝牙关闭、云台重启、PDF 打开、应用后台恢复。不要以固件更新作为兼容性测试。

### 7.4 验收标准对应关系

静态构建与包结构已通过；安装、启动和云台行为全部待真机确认。

## 8. 风险、依赖与回滚

### 8.1 风险与缓解措施

候选库是第三方预编译构建，未从源码独立重建，也未确认其底层 PDFium 的确切版本；以固定提交和文件哈希记录来源。JNI 静态核对不能替代运行时检查。

### 8.2 前置依赖与阻塞项

本地构建已完成；完整验收受真机不可用阻塞。后续更新需要保存相同签名密钥。

### 8.3 回滚方案

卸载兼容版，使用保留的原始包。卸载会清除 App 数据。

### 8.4 兼容性说明

本地签名、ARM64 专用、旧目标 SDK 兼容测试版。
